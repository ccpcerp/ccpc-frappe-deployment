## 2. Accepted accounting intent and boundaries

**Operational business fact confirmed:** Ricor's departments/equipment *consume* these materials directly; this transaction has **no Ricor warehouse receipt/inventory recognition step**. Consequently the intended purchase-side ledger is, subject to separate accounting-policy/amount/tax/fiscal validation:

| Ricor Purchase Invoice `ACC-PINV-2026-00005` | Expected accounting upon separately approved eventual submission |
|---|---|
| Debit | `5150 - Intercompany Materials Expense - RMC` |
| Credit | `2121 - Intercompany Payable - RMC` |
| Posting date / amount | Original frozen billing period-end and unchanged approved amount, subject to exact source/base currency and tax signoff |
| Stock Ledger | **No new Ricor SLE** from this direct-expense billing invoice |

CCPC retains the original submitted Material Issue, its immutable original stock Item and valuation/Department evidence and the separately created Draft SI `ACC-SINV-2026-00001` with proposed Dr `1312` receivable / Cr `6050` material charges on eventual authorized submission. Existing CCPC Material Issue stock/GL entries are **separate prior postings**: reconcile actual issuer expense/stock valuation to the intercompany billing and consolidation elimination policy; never count them as an extra Ricor stock issue or assume group expense equals the sum of both entities' gross expense. **No GL has been posted for either new invoice yet.**

**No shortcuts:** No global `Item.is_stock_item` conversion; no fake Ricor Purchase Receipt; no `is_opening` or `update_stock` manipulation to coerce accounts; no direct SQL edits to PI lines/GL, arbitrary Account master rename, user grant, unexplained Journal Entry, balance adjustment, invoice deletion/recreation, current-batch refresh/re-approval, or overwriting original source claims.

## 3. Proposed future-batch data and accounting design (app changes only after review)

1. **Original immutable material evidence stays stock-based.** Keep `Intercompany Material Billing Item.item_code`, `stock_entry_detail`, `stock_entry`, Withdrawal Slip Item, quantity/UOM, frozen Basic Rate/Amount, dates, original requesting/work-for Department/Section and Equipment. Claim one source line only once, as existing guarded code does.
2. **A distinct controlled non-stock *billing representation* for Ricor PI only.** Use an approved dedicated `Item` with `is_stock_item=0` for **directly consumed intercompany material charges**, without changing the stock Item master. Item must be enabled, non-fixed-asset, without deferred expense or stock behavior, and have compatible UOM. To support unlike units/items, approve an explicit source Item Group + UOM → non-stock billing Item mapping (or a more specific scoped mapping where needed); **never substitute a generic `Nos` item for kg/litre/bag quantities without a justified conversion**. The invoice must display material/source details without misrepresenting the non-stock billing Item as an actual warehouse receipt.
3. **Reuse signed Finance mappings where possible.** A separately approved `CCPC Expense Mapping Scope` / `Revision` for **Ricor Company + original source Item Group** must resolve uniquely to active Ricor leaf expense `5150`, using approved effective dating and signed decision evidence. Ricor's **beneficiary Department→Cost Center** must likewise resolve through actual Ricor-scoped approved Center mapping; original source `requesting_department` / `work_for_department` may be CCPC-scoped and must not be silently reused across Companies. Explicit authorized cross-Company beneficiary crosswalk is required if source Dept is not already Ricor-owned. Require exact signed/active snapshot, no generic Company default fallback, no implicit Department.
4. **Durable line-level traceability:** Original-source Stock Entry Detail / original stock Item and its UOM/rate/quantity, original Withdrawal Slip Item, chosen non-stock billing Item, associated effective mapping revision(s)/signed Accounting decision, Ricor beneficiary/cost center, calculation basis, and original PI item row name must be bound in a versioned, restricted accounting correction/mapping evidence record. Future source-to-invoice reporting must join on that binding rather than assume PI `item_code` equals stock `item_code`. Where new read-only invoice-line custom fields are proposed for convenient display, protect them against client-supplied changes and verify authoritative source server-side.
5. **Native Frappe persistence validation:** Construct Ricor PI item with the non-stock billing Item, original frozen quantity/UOM/rate, `expense_account=5150`, approved Ricor Cost Center and beneficiary Department/Equipment operational context. Call *normal* native `PurchaseInvoice.insert/save/validate` under explicitly scoped server authority. **Reload the inserted/saved item**, assert `item_code` is approved non-stock billing Item, `expense_account` is still exactly 5150 and Root Type Expense, exact Ricor Company/UOM/qty/rate/base/amount/tax state, no SLE, and matching SI/PI totals and reciprocal links. Fail closed and roll back pair if native validation changes any authoritative accounting value. Validate applicable taxes and intercompany tax policy separately; the previous Drafts having zero tax does not itself determine tax legality.
6. **Posting and reconciliation are not part of the Draft generator.** No invoice submission or GL/SLE posting in this change. Later native `submit()` requires a separate named Accounting submitter with effective DocPerm/Company permission, verified historical period, credit/party/tax and side-effect review, plus a **new post-Draft local+off-host verified backup**.

## 4. Existing persistent Approved batch + two Drafts: a NEW narrow audited correction path

The current real MAIN DEVELOPMENT batch is not an empty new batch. **Do not rerun its one-time approval or delete/recreate invoices.** A design for this exact state must:

1. Use a **purpose-specific approved-Draft direct-expense correction request/decision** separate from existing *cancelled-pair* correction. A proposed private DocType with no general Create/Write/Delete and append-only decision-use events could record: batch name and original immutable source fingerprint, exact SI/PI names, exact original PI Item row ID and old stock item + `2301` account, proposed non-stock Item + `5150`, frozen qty/UOM/rate/totals and period, signed mapping revision and Ricor Cost Center, reason, actual named correction requester, distinct named Finance Controller approver and timestamps, pre/post fingerprints and application status. Give the new workflow a unique one-use key `(batch, purchase_invoice, source_item_row)` with a DB uniqueness constraint to prevent duplicate application. A *documented proposed schema* is not evidence it exists or permission to migrate it.
2. **Maker/checker:** require a real enabled named correction requester with both Companies' generic User Permissions and an approved preparer role, and a *different* enabled named Finance Controller with both Company grants, no Stockroom role; native batch + invoice DocPerm and current user authorization checked server-side. **Original synthetic DEVELOPMENT maker is not an acceptable new human correction requester.** A human-authenticated web approval in the future is distinct from an operator `frappe.set_user(...)` session and must not be overclaimed.
3. **Transactional one-time application after separate owner authority:** lock batch, both invoice rows and correction case in a documented consistent order, reject concurrent/replayed correction, reject if either invoice no longer `docstatus=0`, any GL/SLE/payment/allocated advances/linked-return or unapproved active correction exists, or original source/amount/links/taxes/currency/period/Company/parties have drifted. Preserve original `Approved` status and `approved_by`; **append** new correction approval separately. Update only the Ricor PI's *one affected Draft item* to the authorized non-stock billing representation via native Frappe document save (not manual SQL); maintain original SI and PI names, reciprocal links, source batch identities, quantity, rate, grand totals, posting date and all protected financial flags. Revalidate and independently reload all fields/ledger counts. A single SQL transaction/commit includes the application decision, Version evidence and PI Draft correction; on any precommit failure rollback all. A postcommit uncertain state is **STOP/no retry** until independent read-only inspection.
4. **Audit and reversibility:** preserve immutable prior-account and prior-item snapshots, full reason/decision ID and Version audit. If applying changes to a Draft PI is not safely supported by native hooks, prefer a separately reviewed deliberate Draft-void/supersession workflow preserving old IDs and references **without deleting invoice or releasing source claims**, not hidden reset or ad hoc cancellation. No assumption a submitted/cancelled path is valid for Drafts.
5. **Do not silently change other financial records.** No Company GL, Stock Ledger, journal, chart of accounts, Item type, stock receipt, global defaults, prior Material Issue, another invoice, or other batches altered. Any migration or new Item master creation needs separate operator approval, post-Draft recovery, and isolation from PRODUCTION.

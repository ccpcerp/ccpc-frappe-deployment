## 2. Non-negotiable execution boundary and evidence handling

**No command in this plan is preapproved to run.** The phases below are future **gates** and suggested evidence, not instructions to execute now. Every first transition from source review into real command execution requires a **new explicit owner approval naming target, precise action, risks, rollback and expected artifacts**. Keep the first live test entirely off shared CCPC physical infrastructure where feasible.

The preferred fixture is a **disposable, strongly isolated Docker/Frappe laboratory** with synthetic non-business records, isolated volumes/network, no CCPC real site config/secrets, no Synology credentials or mount, no access to production private files, no production SSH mounts, no host Docker socket shared with active CCPC production, no DNS/ports that can route to production, and no reused Compose project, volume or container names. Establish the **actual** isolation method and permission boundary before authorizing a build or test. A shared Docker daemon or host-mounted socket is **not** adequate isolation merely because Compose project names differ; if adequate isolation cannot be established, **STOP** and revise the plan.

The production policy hardcodes the expected host `ccpcerp-prod` and site `ccpcerp.local`. A disposable test must **not** weaken production validation or spoof a real production release to obtain `backup_ready=True`. Use an explicitly distinguished **test-only harness/fixture** for checks independent of physical host, plus an authorized later dedicated-host acceptance for the genuine fixed-host check. A synthetic site may have the same internal Frappe site string **only inside an isolated namespace** with no production data or routing, clearly marked as a fixture. All generated run IDs, approval keys, release identifiers, image IDs, DBs and records are test-only.

Record a **sanitized evidence bundle** per gate: GitHub repository/ref/full commit, Compose version and file order, test case ID, redacted command class, observed PASS/FAIL, exit code, reviewed blob/config/image identities where safe, rollback action/result, reviewer, and explicit **limitations**. Never commit passwords, private keys, tokens, full environment dumps, databases, site_config contents, Docker credentials, raw private file archives, NAS mount credential files, business data or unrestricted logs. Use protected off-Git storage for raw test artifacts where absolutely necessary. A FAIL/uncertain state is an **immediate stop**, not permission to retry destructive actions.

## 4. Proposed negative/adversarial test inventory

These cases must be assigned explicit test IDs and pass/fail evidence in the future laboratory, in addition to happy-path checks:

- **Correct target fail-closed:** wrong hostname/site/project or multiple backend/db instances; source image IDs/config hashes mismatched; spoofed Compose labels; stopped/unhealthy MariaDB; Docker socket or unexpected mounts exposed; backend anonymous `logs` from image `VOLUME`; other workers unintentionally retaining anonymous logs.
- **Approval trust fail-closed:** missing public key, self-signed trust root, reviewer==preparer, unsigned/altered release digest, revoked key/release, stale high-water sequence, expired snapshot or replay inside the permitted window, trusted UTC source unavailable.
- **Consistency fail-closed:** concurrent upload and DB record, in-flight stock/accounting posting, long-running job, queue retry, scheduler or inbound integration; repeated backup run, Frappe backup defaults deleting unexpected files, partial filters, missing encryption recovery.
- **Publication fail-closed:** CIFS outage or disconnected mount, interrupted copy, hash corruption, partial/complete collision, NAS exhaustion/permission denial, concurrent run/lock failure, rename lacks `RENAME_NOREPLACE` support, remount replacement and local-dir fallback.
- **Restore fail-closed:** missing site config, DB dump or private/public files; mixed run IDs, incorrect permissions, unreadable private attachments, incorrect site-to-DB link, recovery secrets missing, unexpectedly required migration, retention deleting only known-good recovery point.

## 5. Rollback and abort strategy — deliberately non-destructive

1. **Before execution:** record exact lab scope, unique Compose project/volume/network names, intended source commit, owner of test resources, snapshot state, **test-only** backup of lab fixtures, and separately approved resource cleanup list. Keep approval record and no-secrets recovery contact outside the disposable environment.
2. **At any failure:** stop the **particular gate**, record error sanitization and state, prevent scheduler/retry/release advancement, and retain partial captured evidence privately. Do **not** forcibly shut down unrelated services, delete backup directories, assume retry idempotence or treat Docker/SMB errors as proof of rollback.
3. **Restore lab:** if specifically approved, roll back to the **exact recorded test-only** image/config and re-create only named disposable fixtures whose ownership is proven. Recover fixtures from a pre-test snapshot, verify consistency, and confirm no external endpoints. The exact rollback commands must be reviewed **after** inspecting the environment; no blanket `docker compose down -v`, `docker system prune`, `rm -rf`, `git reset --hard`, force push or general directory clean.
4. **Volume lifecycle:** the named `logs` volume is **new** in the dedicated overlay. Never assume historical image-declared anonymous `logs` volumes are empty or disposable; inventory before migration and preserve them until separately reviewed. Never remove `sites`, `db-data`, Redis data, private logs, mounts or credentials on an existing host under a test cleanup.
5. **Recovery handback:** independently verify services/fixture integrity, no dangling privileged Docker socket access, no persistent scheduled job or mounts, test-only secrets destroyed by approved means, and sanitized test report in GitHub. An uncertain teardown is a **blocker**, not success.

# CCPC ERPNext — Approved incremental, usable-first rollout strategy

**Decision date:** 2026-11-17 (Asia/Manila). **Owner-approved strategy:** make ERPNext *usable first*, introduce small business features in independently accepted increments, and **defer complex CCPC↔Ricor intercompany billing** rather than withholding all value until the entire custom application is finished. This supersedes the prior proposed months-long *all-features-first* release sequence. The prior owner confirmation also established **same-Company stock/beneficiary-only** for initial Departmental cost phase. **Not** an authorization for any particular PRODUCTION database write, container operation, migration, new release, credential setup, image build or go-live date.

## Product delivery levels (do not confuse them)

| Release | Minimum immediately useful outcome | Exclusions / acceptance boundary |
| --- | --- | --- |
| **R0 — Native ERPNext controlled pilot** | Reuse a *verified*, suitably secured ERPNext installation with selected users and one real Company. Stock/Item/Warehouse, standard Material Request (where applicable), Stock Entry Material Issue, Cost Center, standard Stock Ledger and General Ledger/P&L reporting. Use clearly identified test or pre-go-live trial data until live accounting cutover is separately signed. Verify transaction roles and source references. | **Not** CCPC Withdrawal Slip automation, certified Department expense attribution, or intercompany billing. Standard ERPNext Material Request and Material Issue do not by themselves establish CCPC's exact atomic Withdrawal-to-Stockroom authorization; do not represent manual controls as automated. |
| **R1 — Same-Company Withdrawal and Department accounting** | Approved CCPC Withdrawal Slip with independent Stockroom issuance, signed Company+original Item Group→Expense Account and beneficiary Department→Cost Center mapping, real Stock Entry/SLE/GL, Department dimension, and a source+GL reconciled Department cost report. | Exclude new cross-Company financial issues and intercompany batch/SI/PI automation. Report raw SLE value separately from posted GL expense, with source exceptions. |
| **R2 — Equipment, advanced reporting / workflows** | Add individually tested Equipment/Job activity and Company expense reconciliation, appropriate Department reader access, workflow/returns enhancements. | Can deliver per feature; do not hold the whole installation for optional functionality. |
| **R3 — Intercompany** | Resume original CCPC→Ricor billing, direct-consumption PI representation, signed historic policy, corrected Draft transaction, GL/AR/AP reconciliation and carefully controlled cutover. | Existing DEVELOPMENT approved batch and original Draft SI `ACC-SINV-2026-00001` and PI `ACC-PINV-2026-00005` are preserved on hold. No replay or synthetic historic Finance signoffs. |

**Current decision:** Prioritize R0 first, then R1. R3 work can remain in draft PRs #33/#34; the saved CircleCI `CCPC_RICOR_APPROVED_SHA` does not start a run, and the planned paid Ricor SQL job is **not** on the first-release critical path.

## Existing install — fastest candidate, NOT yet go-live approved

GitHub [ccpc-project-context.md](ccpc-project-context.md) records an **existing old-host legacy PRODUCTION** Compose project `frappe_docker`, Frappe site `ccpcerp.local`, internal hostname `http://ccpcerp.com`, LAN-only documented login access on port 80, and NAS production backup script history. This is **historical owner-observed evidence**, not a fresh Nov 17 site check. Old production and DEVELOPMENT share the `ccpcerpserver` **physical host/Docker daemon**; logical Compose separation is not absolute physical isolation. Do not expose administrative credentials, privileged internal paths or live accounting records in logs/chat.

The newer **dedicated** `ccpcerp-prod` Ubuntu host has independently reported SSH/UFW hardening, but the current [production host handoff](PRODUCTION-HOST-SETUP-HANDOFF.md) does **not** verify installed ERPNext/TLS, current Compose render, consistent backup, restore or business-data cutover. Do not invent live dedicated-host status. Never substitute unverified migration/restore for the existing working installation.

**Two fast routes after a single read-only current-state comparison:**
- **A — fastest limited internal pilot using existing old PRODUCTION stack** *only if* current app/service version, site health, HTTPS or explicit restricted-access alternative, named user permissions, data/financial configuration, latest NAS+local recovery, independently workable restore, and shared-host resource/isolation safeguards are verified; separately approve risk and live data start. Use only a small authorized group initially. Do not erase/overwrite prior records or migrate a new custom-app branch as a shortcut.
- **B — dedicated-host path** if legacy host cannot meet minimum security/recovery or the existing business database must remain unchanged. Finish current Compose/TLS/secret/backup/restoration checks and stage a new site. May take longer; never silently copy old production business data or credentials.

## Smallest defensible native ERPNext pilot

1. **Read-only reality check first**, one short operator batch with no modifications: identify Docker project/container status, actual Frappe/ERPNext site+app versions, existing Companies and stock/accounting setup at summary/count level, latest *usable* four-part backups (DB, config, public/private files) and NAS mount, current LAN access/HTTP-vs-HTTPS, user roles, resources and installed custom app/patch state. Never export passwords, personal details or business line records; do not issue `bench migrate`, `bench update`, `docker compose up`, `bench restore` or submit Stock Entry as diagnostics.
2. **Choose pilot Company/people and set an accounting start boundary**, no cross-Company consumption, real Expense Account/Cost Center/Department Dimension if certified, Warehouse/Item/UOM/stock quantity and valuation baseline, fiscal period. One responsible named finance approver and separate stockroom operator; verify user permission and backup/restore plan before first posting.
3. **Pilot only standard ERPNext flows:** Material Request as demand/documentation where appropriate; Stock Entry **Material Issue** for physical deductions; review resulting native Stock Ledger and General Ledger using transaction and Cost Center/Department filters. Official ERPNext docs: [Material Request](https://docs.frappe.io/erpnext/material-request), [Stock Entry](https://docs.frappe.io/erpnext/stock-entry), [Accounting Dimensions](https://docs.frappe.io/erpnext/accounting-dimensions). Material Request alone is **not** a stock or ledger posting, and native Stock Entry's Material Issue does not automatically mean an independently linked/approved CCPC Withdrawal Slip. Do not claim certified per-Department GL cost unless the accounting dimension, expense account, cost center and actual ledger evidence are observed.
4. **Prove 1–2 representative controlled transactions** with named roles, correct Item/UOM/warehouse, quantity change, SLE valuation and Expense GL, mandatory beneficiary Cost Center/Department, no cross-company spill, cancel/error route, report consistency and full backup. First use an isolated site/test fixture; any real PRODUCTION document creation/submission requires separate explicit go-live authorization and transaction signoff.
5. **First live user access** only after operator shows current authenticated HTTPS (or owner accepts a separately documented restricted trusted-LAN interim security posture), backup and independent restore-readiness evidence, exact user roles, and no unresolved accounting stop. Train initial staff and prevent parallel duplicate offline/legacy entry during cutover. Record immutable go-live date, actual branch/image/SHA/app versions, and rollback owner.
6. **R1 custom release** is separate and narrowly changed: exact-source Phase 1 GitHub code reviewed; server-side block of cross-company Withdrawal issues; signed Expense/Center mapping, row locks, transactions, reports and real native integration PASS; backup+controlled DEVELOPMENT acceptance; then distinct reviewed release and production approval.

## Schedule planning — optimistic working targets, not deployment promises

- **Within 1–3 focused working days:** complete read-only system/recovery/access inventory and select existing vs new host; plan the first pilot and data boundary (depends on operator time and current live state).
- **Approximately 1–2 weeks for controlled R0 pilot** if the *existing installation* is healthy and already meets or can quickly meet account security, recovery, stock valuation and restricted pilot-access requirements. **No date guarantee**; may be faster in a test/DEVELOPMENT environment, longer for true live accounting.
- **R1 departmental accounting and custom Withdrawal:** work in short weekly or smaller increments after exact-source integration, actual Finance mapping/roles and safe DEV tests. Additional weeks are plausible, not a fixed long multi-month hold for each addition.
- If dedicated host or security/restore is not ready, **do not skip the gate to hit dates**. The earlier broad full-feature forecast and 40% ±10-point scorecard remain historical scope; R0 and R1 require **their own** readiness checkpoints. Deferring work changes denominator, not proof of implemented progress.

## Release rhythm and rules

- Ship a feature only when its **specific** isolated/DEVELOPMENT behavior is proven, documented, permission checked and recoverable. Bounded rollback/recovery rehearsed for any accounting/stock-impacting upgrade. Avoid migrations bundled with unrelated experiments.
- Use GitHub for code, current review PRs for unfinished work, and exact operator-reported live results for site state. Do not assume a draft PR is deployed. Preserve existing DEV and old/new PRODUCTION data and unknown changes.
- No automatic/paid CI, scheduled publishing, force pushes, LIVE financial posting, deployment, restart, migration, rollback or database restore simply because this strategy is approved. Each real production-impacting operation still needs **explicit exact-scope owner permission**.
- If R0 can operate without activating the unreviewed custom app features, do not couple the first ERPNext pilot to current intercompany PR #34 or to the draft-report merge. Never hide unsafe server endpoints in the UI and call that disabled: verify permission and feature enforcement at the server.

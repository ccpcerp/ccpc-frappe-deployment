## Boundaries and explicit release gates

**DO NOT** on the basis of this design alone: enable service units, apply Docker restart policies, call `docker start`/`stop`/`restart`/`update`, run Compose up/recreate, pull images, copy secrets, migrate, reset credentials, run SQL, restore/copy data, start job/email workers, reboot, alter firewall/DNS/certificates, merge a deployment PR, change OLD PROD/DEV or proceed with employee go-live. All Stage3A/3R/3S/3T and NAS one-use backup executors already consumed; **NEVER RERUN**. This design addresses only G1 resilience and does **not** waive G2–G7 business/security/cutover checks.

## Failure modes and proposed strategy

| Failure mode | Current behavior / risk | Review proposal, not implemented |
| --- | --- | --- |
| Container process exits while dockerd stays running | `RestartPolicy=no` means no guaranteed automatic container restart | Consider narrowly changing restart policies on **only** six exact saved candidate IDs to `unless-stopped`, after validating the consequences of unexpectedly resuming backend services; verify per-container policies and record rollback `no`. No replacement containers |
| Host reboots / power lost | Docker daemon enabled but six containers have `RestartPolicy=no`; Caddy and socket disabled at boot | A single NEW-only, root-owned, versioned startup gate with guarded Docker/DB/Redis/app readiness before it starts only **existing** gateway socket and Caddy; do not boot-enable Caddy/socket independently until that gate is reviewed |
| MariaDB takes longer to initialize | App may run before DB is ready even if all containers auto-start | Bounded health polling (DB Docker health=healthy), then Redis +PONG and backend/frontend HTTP200; websocket TCP9000 or a deeper Engine.IO handshake; failures timeout and alert without SQL changes |
| Relay points at stale `172.20.0.7` | Service may forward to wrong private endpoint after a network/container change | Guard exact original candidate frontend container ID, the sole internal network and exact six member IDs, frontend actual IPv4 and relay target `172.20.0.7:8080`; mismatch -> gateway **not activated** on fresh boot, alert and require human review. Consider later replacing hardcoded IP with reviewed stable service discovery |
| Site jobs/email unintentionally active | Pre-cutover duplicate activity | At boot and before gateway activation re-check `pause_scheduler=YES`, `mute_emails=YES`, no unexpected candidate services; later employee cutover has its **own** approved procedure to change these intentionally |
| Boot check or application probe fails | Misleading “service started” could expose partial system | Fail closed (exit nonzero, no new gateway activation); log only sanitized status; no automatic restore, DB migration, queue purge, service restart storm, volume rewrite, Docker cleanup or old-host switch |
| Service fault after successful boot | A one-shot boot gate cannot guarantee continuous availability; front-end/gateway may show 502 | Define heartbeat/alerting and operation-response runbook separately; Docker restart policy is not a substitute for job/error monitoring or backup verification |

### Proposed controlled implementation stages (ALL NOT AUTHORIZED)

**Stage R0 — Freeze and source-review preflight, read-only.** In GitHub implement a strict source-audited manifest matching the actual existing NEW host/username, six exact candidate container **IDs** and image IDs, private network ID and six endpoints, exact named Docker volumes, live relay target/socket, Caddy LAN bind and firewall disposition, both effective paused/muted site flags, 12 protected original containers, and no unexpected candidate resources. Script must default to non-executing, print only safe markers and STOP on mismatch. Pin the exact reviewed commit and no-network-download source transfer with SHA256 check. Do not inspect/output protected environment, auth tokens, cert keys, site config or business rows.

**Stage R1 — Decide one restart ownership model before changing anything.** Recommended candidate to review: Docker `unless-stopped` for exact six original candidate IDs to recover from unplanned process exit and host restart, with no Compose recreation and unchanged live container UIDs/volumes/networks; **only** if pre-cutover jobs/integrations are independently judged safe and timeout/repair behavior is documented. Do not apply yet; no `docker update` until the owner explicitly approves exact scope, preview, rollback. Alternative is a dedicated systemd-only ordered starter with `RestartPolicy=no` retained (could avoid parallel starts but will need a separate crash-recovery strategy). Do not combine two independent managers that start/stop each other unexpectedly.

**Stage R2 — Boot-gated gateway.** Prepare a new, reviewable root-owned systemd one-shot gate that runs **after Docker**, validates exact current candidate identity/storage/network/site flags, bounds DB/Redis/backend/frontend/websocket readiness polling and confirms private `172.20.0.7:8080` target, then starts **only** already installed `ccpc-erpnext-upstream.socket` and `caddy.service` if every gate passes. Design systemd relationships so the gate itself can be enabled at boot without Caddy/socket being separately enabled or forming cycles. Preserve `ccpc-erpnext-upstream.service` as static socket-activated and `caddy-api.service` masked. Exact current source units and installed file modes/identities need verification. Never publish Docker ports or change LAN scope. Distinguish startup after reboot from an on-line inspection while gateway is already active: gate must not kill healthy current services on a failed read-only preflight. Failures require manual investigation.

**Stage R3 — Staged approval and rollback.** Owner reviews exact source diff, container ID manifests, command-level effects, filesystem changes, and separate rollback, then explicitly approves any live NEW-only change. After each approved mutation immediately verify that the six pre-existing container IDs/data volumes/networks remain unchanged, original 12 and isolated restored 7 remain preserved, `pause_scheduler` and `mute_emails` remain enabled, gateway only LAN-restricted HTTPS, guest/WAN denial not weakened, and no unauthorized worker/mail activity. Rollback for any prospective restart-policy change is restoring exact saved `no` policies to only exact original candidate IDs **without stopping them**; for systemd enabled-unit changes return to prior `disabled` where appropriate without stopping existing working runtime unless separately approved. Never “fix” a mismatch with `compose up` or restore.

**Stage R4 — Operational reboot test only by a different explicit approval.** Review current NAS backup recovery, physical console fallback, power/UPS conditions, downtime notice, current OLD PROD/DEV insulation, and safe rollback, then arrange a supervised NEW-only maintenance window. A reboot is **not** included in read-only readiness or Stage R1/R2 approval. Post-boot compare exact candidate IDs and named volumes, DB+Redis+app readiness, site paused/muted flags, loopback relay IP match, HTTPS/Windows browser, absence of unapproved host-published ports, and all protected original/rehearsal/drill containers. Do not claim automatic reboot recovery PASS without a real, owner-authorized reboot test.

1. **Mapping Maker/Checker already has independent identities and explicit Company grants.** `ccpcerp/ccpc_erp/bc_mapping_workflow.py` calls `_real_authority(preparer, "CCPC Mapping Preparer", company)` and `_real_authority(checker, "CCPC Accounting Mapping Approver", company)`, then `assert_independent_review(doc.owner, checker)`. `bc_issue_runtime.py::_real_authority` requires an enabled named User, explicit Has Role record, specific `User Permission` for `Company` with `apply_to_all_doctypes=1`, and denies Stockroom Personnel and Administrator/Guest. Build #131's eight Finance tests use separate synthetic Maker and Checker users and affirm signed decision audit/rollback. Actual persistent DEVELOPMENT role and Company grants remain unverified.
2. **Billing batch preparation and approval do not yet enforce separate humans.** `ccpcerp/ccpc_erp/doctype/intercompany_material_billing_batch/intercompany_material_billing_batch.py::finalize_month` requires `self.check_permission("write")` and saves `finalized_by=frappe.session.user`. The method `approve_and_create_invoices` calls `_require_finance_approver`, requiring write permission plus `Finance Controller` or `System Manager` role; `Administrator` is a role-check exception. It **does not compare `finalized_by` with the logged-in approver** and does not directly call `_real_authority` or require an explicit `User Permission` for **both** issuing and requesting Company. The DocType JSON grants create/write/read to `Finance Controller` and `System Manager`; the client script also shows both actions for these roles. This is a **maker-checker and explicit company authorization policy gap**, not proof of an exploit: native Frappe User Permissions could impose additional limits, but no actual user/Company test is yet available.
3. **A position title is not an assigned Frappe role.** Billing batch requires the literal Role `Finance Controller` to be assigned on the user's `Has Role` table (unless `System Manager`); the role is distinct from the user's job title. The account role membership reported previously is insufficient to verify the real Finance Controller's access. **Read-only check on DEVELOPMENT required** before any role grant.
4. **Invoice creation is intentionally draft-only and transactional.** Billing approval creates one Sales Invoice / Purchase Invoice pair with cross-references through a savepoint; ERPNext posting and cancellation happen separately. Build #131 confirms real native `submit()` GL posting and native `cancel()` reversal on the synthetic site, permission denial for a synthetic non-Accounts user, and unchanged original Withdrawal Stock Entry/SLE/GL. 5. **Cancelled paired invoices retain batch reservation, with no approved correction workflow.** After both linked invoices are cancelled, the test explicitly asserts both batch references are retained. `IntercompanyMaterialBillingBatch._validate_status_transition` only permits `Draft/Under Review -> Cancelled` when no protected invoice/approval fields, while `Approved -> Cancelled` is forbidden. `_get_active_source_claim` treats every batch whose status is not `Cancelled` as holding the source Stock Entry detail. The DocType declares `Invoiced` status but current transition logic has no operational `Approved -> Invoiced` service path. Therefore the current state is **fail-closed against automatic rebilling**, but there is no established procedure to correct an approved batch after native SI/PI cancellation; reporting semantics of `Approved` vs actually posted/cancelled invoices must be specified.
6. **Real invoice posting rights are not the same as billing-approval rights.** In Build #131 the real draft-to-submitted and cancellation tests use a synthetic site and Administrator for native invoice posting. ## Original policy proposal (historical; owner approved 2026-11-03 for draft implementation)

**A. Two-person billing approval:** a named Billing Preparer can create/refresh/finalize the monthly batch; an independently named Finance Checker with the approved authorization role and scoped Company grants can approve and create draft invoices. The checker **must differ from** `finalized_by`; prevent self-approval including any API path. No stockroom user can approve. Decide the exact preparer/checker roles and whether System Manager/Administrator retains any formally audited break-glass exception. Both issuing and requesting Companies must be explicitly authorized according to Accounting's agreed access matrix; do not silently grant cross-company rights.

**B. Invoice posting separation:** drafts remain drafts until separate, named, authorized accounting users review and submit the Sales and Purchase Invoices under ERPNext's native DocPerm and Company restrictions. Neither billing approval nor the checker may bypass native submit/cancel authorization. If the same individual is proposed to approve a batch and post invoices, Accounting must expressly confirm that role combination and its compensating controls.

**C. Cancelled-pair correction:** keep source rows reserved and the original invoice links/audit intact after a cancellation; **no automatic rebilling or silent clearing of financial links**. Introduce a distinct, audited Finance approval process for a replacement pair or an ERPNext-standard correction/credit-note path, preventing duplicate amounts across Companies, requiring reason and both invoice states, and preserving references to original documents. Specify behavior when only one invoice is cancelled, when an accounting period is closed, and when corrected invoices are submitted or cancelled again. Clarify whether batch `status` should remain `Approved` with derived invoice status or gain an explicit controlled `Invoiced/Voided/Replaced` lifecycle. Do not implement until Accounting approves one design.

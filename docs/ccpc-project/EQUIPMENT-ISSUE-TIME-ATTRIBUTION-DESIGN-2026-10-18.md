### Source-code conclusions

1. **A plain Equipment Link field is not a truly independent issue-time snapshot.** At pinned Frappe commit `4515014c87ece6cb20ee91d2cfb121c5cbd1ff4a`, `frappe/model/rename_doc.py` `update_link_field_values()` rewrites Link field values via `frappe.db.set_value(..., update_modified=False)` during rename; `get_link_fields()` includes custom Link fields. This update is outside an individual Stock Entry's normal controller validation. Therefore a proposed `ccpc_equipment_at_issue` **Link** can follow a later Equipment Registry rename and is **not, by itself, an unchanging record of the identifier originally presented at issuance**.
2. **Existing Equipment Registry rename protection has an attribution blind spot.** [Equipment Registry `has_protected_equipment_history()`](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/ccpc_erp/doctype/equipment_registry/equipment_registry.py) examines Equipment Asset Assignment and existing Equipment fields on selected submitted accounting/stock rows, plus an optional GL Equipment field. It **does not query linked, submitted Withdrawal Slip → Stock Entry issues by `Withdrawal Slip.equipment`**. Because native pinned ERPNext Stock Entry/Detail has no Equipment field and CCPC's withdrawal schema setup does not provision one, a posted Equipment usage **may not be detected** by this rename guard. Confirm via guarded synthetic integration tests before calling this exploitable on any deployed site.
3. **No guaranteed permanent Equipment UID exists in the reviewed master schema.** `Equipment Registry` uses `autoname = field:equipment_number`, while `equipment_number` is editable only via Rename. No separate guaranteed immutable machine identifier has been verified. `serial_number` exists but is not shown to be required or unique; do not use it as a canonical identifier without a master-data audit.
4. **Existing provenance links are helpful but incomplete.** The issue source has a submitted `Stock Entry` header `withdrawal_slip` Link and row `withdrawal_slip_item` Data created by `ensure_withdrawal_slip_stock_entry_fields()`. The SLE source row is connected by `voucher_no` and `voucher_detail_no`. The source Slip controller normally disallows post-approval Equipment changes, and real disposable [CI run `39092809713`](https://github.com/ccpcerp/ccpcerp/actions/runs/39092809713) passed **6/6 real tests**, including normal after-issue edit denial and multi-Equipment SLE grouping. None of those tests establishes an independent on-voucher Equipment snapshot or defenses against direct SQL edits/renames.
5. **Accounting remains separate.** Draft [PR #14](https://github.com/ccpcerp/ccpcerp/pull/14)'s real test of original Material Issue beneficiary Department attribution still fails; approved accounting policies A–C do not identify exact expense accounts or Cost Centers. A correct Equipment reference never excuses that posting problem.

### Recommended model to review before implementation

**Preferred staged design: two distinct per-item source fields on `Stock Entry Detail`, subject to separate approval and verified metadata review.**

| Proposed field | Frappe type | Intended meaning | Important limitation |
| --- | --- | --- | --- |
| `ccpc_equipment_at_issue` | Link → Equipment Registry | Validates which actual Equipment Registry record was used; convenience navigation and consistency against issue Company | Link values may be rewritten by normal Frappe rename, so this is **not** the historical source code by itself |
| `ccpc_equipment_code_at_issue` | Data | Capture the exact original Equipment Registry `name` / equipment number **once at issue creation**, for durable historical text/provenance | Not a globally permanent asset UUID; direct SQL can still alter it and a corrected/renamed identifier needs an alias/mapping history |

Both fields would be **read_only=1** and **no_copy=1**, deliberately **not required on every Stock Entry Detail globally**: ordinary unlinked stock transactions and CCPC non-equipment withdrawals must continue to work. For **new linked equipment-attributed original Material Issues**, enforce both populated together, matching authorized Slip at submit, correct issue Company, and consistency across its stock rows. For a legitimately *non-equipment* issue, both remain blank; no fallback to the requester Department or today's Equipment Registry assignment. Never interpret absent historic fields as a zero Equipment cost.

**Write-once is a server-side invariant, not merely UI styling:** original issue builder would populate values atomically from a validated Slip; validate linked voucher and row source, forbid client/API changes and field clearing after creation; recheck under the existing posting transaction/Slip lock at submit. Preserve submitted and cancelled transaction history; report joins to the **exact submitted `Stock Entry Detail.name`** and uses the persisted Data snapshot for historic grouping, while reporting Link/Data disagreements for review. Protect against duplicate credit/return issuance. Privileged raw SQL/DocPerm patching can bypass application validators, so access restrictions, backups and separate reconciliation/audit checks remain essential. Frappe rename/link rewriting must be explicitly tested, and Equipment Registry rename checks extended to detect **posted Withdrawal Slip-linked issue history**, even when optional legacy `equipment` fields do not exist.

**Future alternative (higher migration cost):** introduce a separate never-renamed `Equipment Registry` identity (e.g., a dedicated immutable identifier) carried to each issue row. That would be stronger across authorized equipment-number corrections, but master migration, repair/replace lifecycle, unique constraints and historic identity mapping require their own design/approval. Do **not** invent a UUID for old rows and claim it reflects a historical original machine without evidence.

### Historic submitted issue classification — recommended conservative policy

This review **does not know how many CCPC historical submitted issues exist** or which optional Equipment fields are configured. Before any write/backfill, run a **read-only** inventory on the correctly verified DEVELOPMENT target (not PRODUCTION) after checking its Git branch/commit/status and target identity. Group by issue Company, posting period, submitted/cancelled state and linked source. Do not dump sensitive business rows or customer/employee details to GitHub.

| Classification | Example evidence | Reporting and repair disposition |
| --- | --- | --- |
| `CURRENT_SNAPSHOT_VERIFIED` | Future new submitted issue row with approved populated pair, validated company/source, posting audit | Eligible for normal per-Equipment attribution, subject to SLE/GL/returns accounting checks |
| `LEGACY_INDEPENDENT_EVIDENCE_REVIEW` | Historic submitted row already has a trustworthy contemporaneous independent Equipment value, cross-checked to Company, linked Slip/item, immutable audit evidence | **Quarantine from certified totals until an authorized reviewer confirms evidence**. Do not automatically copy into new fields |
| `LEGACY_SLIP_ONLY_UNVERIFIED` | Only current `Withdrawal Slip.equipment` is known or current Equipment/Job Order assignment is known | **Provisional/unverified attribution**; keep out of certified lifetime totals until independently reviewed |
| `LEGACY_CONFLICT` | Existing row, header, Slip and/or Equipment Company disagree, duplicate row links or uncertain issue lineage | **Exception queue**; block automatic attribution and never select first-match/current defaults |
| `HISTORIC_UNATTRIBUTED` | Missing Equipment or incomplete source for an equipment-intended issue | Track as **unknown/needs review**, not a zero-cost machine; do not silently assign |
| `NO_EQUIPMENT_INTENDED` | Traceable non-equipment withdrawal purpose explicitly known | Keep in company/Department material expense; do not invent machine attribution |
| `CANCELLED_OR_REVERSED` | Cancelled submitted issue, linked cancellation/reissue or approved posted return | Exclude cancelled issue from active consumption; reissued issue is new source; returns reduce only original validated Equipment at posted original-cost basis |

**Historical cutover rule proposed for accounting/owner approval:** new snapshot controls should apply **prospectively from an agreed cutover date on a verified environment**. Do not make the new custom fields mandatory for historical Stock Entry Details, silently rewrite posted vouchers, or auto-backfill based on current Slip/Equipment master. Historic attribution corrections should instead require documented evidence, two-person review/separation, reference to the original issue/SLE and durable approval trail in a separately designed exception process; **no GL or stock ledger rewrites**. Keep qualified legacy, unqualified legacy and new post-cutover values visibly distinct in the maintenance report, with a missing/exception count and amount where independently known. Cost Center and expense-account exact mappings remain Accounting-controlled.

## Earlier single-Link concept — superseded by the paired-field review above

The following originally proposed safeguards remain useful, but the later **paired Link + independent Data snapshot** is the current recommendation. In particular, a lone Link to Equipment Registry is **not** an independently immutable issue-time identifier because Frappe rename can rewrite Link values. This old section is retained for historical rationale, not separate implementation approval.

1. For each **submitted original** Withdrawal Slip Material Issue row, retain a **write-once, company-validated original Equipment Registry identity** and its linked original Withdrawal Slip **and Withdrawal Slip Item** in the source Stock Entry Detail. Proposed distinct custom Link field `ccpc_equipment_at_issue` or an explicitly authorized existing independent Equipment snapshot field. Do not repurpose a potentially editable current field without proving immutability and migration compatibility. The exact field name and schema are **not approved**.
2. Populate this identity atomically **before Stock Entry submission** from the authorized, validated `Withdrawal Slip.equipment`, preserving the approved original Company and original beneficiary Department. Do not derive it from Equipment's current owning Department at report time or from currently assigned Asset. Enforce consistent item/header Equipment and nonblank provenance for equipment-attributed issues; missing/ambiguous source must fail according to approved exception treatment.
3. Block user/API edits to the stored original identity on draft/submit and subsequent document modifications and enforce original row-link immutability. Submitted vouchers should follow normal ERPNext immutable/cancellation semantics. Administrators' raw SQL still bypasses application validators; restrict database writes, preserve audit logs/backups, and use reconciliation checks to expose inconsistencies. Avoid claiming absolute tamper-proof protection.
4. For each traceable **Stock Ledger Entry** from the submitted Material Issue, join by **exact** `voucher_no` and `voucher_detail_no` to its original item. The maintenance report groups by **issue-time snapshot**, not mutable current Slip/Job Order/Equipment master Department. Cross-check original Slip and current fields as evidence, flag mismatches for a separate audit report, but **do not silently reallocate historical costs**.
5. For multiple items, partial issues, amendments, cancel/reissue flows, Equipment-to-Asset reassignments and multi-Company cases, preserve source identity per item. Never silently select a fallback Equipment or merge costs from another Company.
6. For historic submitted issue items lacking a confirmed original source identity, choose a **separately approved audit/reconciliation procedure**; report them as **unattributed/needs review**, not as zero costs, and never automatically overwrite financial or inventory history/backfill from today's mutable Equipment value.
7. Authorized physical material returns under Option A must reference original submitted issue row and inherit the **original Equipment identity** and original posted valuation/account/Cost Center/Department. Subtract only independently approved, actually posted accepted returns; protect cumulative quantities, duplicate/concurrent receipts and cancellation reversals; avoid double-counting material and Purchase Invoice transactions.
8. Job Order historical Equipment is also a separate provenance concern; current real report reads `Job Order.equipment` and `date_assigned`. For trustable equipment service history, independently review post-close edit controls, Work Request and Equipment Asset Assignment links. No labor rate, outside vendor cost or downtime estimation is authorized by this snapshot design.

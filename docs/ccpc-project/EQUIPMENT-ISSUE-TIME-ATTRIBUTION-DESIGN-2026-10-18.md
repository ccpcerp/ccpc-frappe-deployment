# CCPC Equipment maintenance costing — issue-time Equipment attribution design

**Date:** 2026-10-18. **Status:** GITHUB SOURCE REVIEW AND PROPOSED CONTROLS ONLY. **Not approved schema or posting implementation.** Relevant review branch [app draft PR #15](https://github.com/ccpcerp/ccpcerp/pull/15). This document does not permit database migration, master-data changes, deployments, role grants, or production operations.

## Business objective

Owner-approved [Decision D](WITHDRAWAL-ISSUE-ACCOUNTING-DECISION-D-APPROVED-2026-10-18.md) requires operational Equipment maintenance-cost tracking to inform **repair-versus-replace** decisions; no new Equipment GL Accounting Dimension is required initially. Approved accounting rules A–C still govern beneficiary Department, item/material expense account and company-specific Cost Center. A repair cost must not migrate to a different machine when Equipment ownership, department, master data, source records or asset assignments change later.

## Verified current behavior and gap

- The current [Withdrawal Slip Material Issue builder](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/ccpc_erp/withdrawal_slip_stock.py) writes `Stock Entry.equipment` and detail `equipment` **only if metadata says the custom field exists**. This branch's [`ensure_withdrawal_slip_stock_entry_fields`](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/setup.py) provisions `withdrawal_slip`, issuer and detail `withdrawal_slip_item`, **not** a guaranteed historical Equipment snapshot.
- Pinned ERPNext v16 native `Stock Entry` and `Stock Entry Detail` JSON have no native `equipment` fields. Depending on the installed site's custom field configuration, issue-row Equipment may not be persisted at all. **Do not infer field existence from a form displaying Equipment or from synthetic setup.**
- [Withdrawal Slip](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/ccpc_erp/doctype/withdrawal_slip/withdrawal_slip.py) includes `equipment` among request-intent fields locked once approval advances. This is a normal **document validation** safeguard; raw database updates (e.g. `frappe.db.set_value`) do not run the same controller validation.
- [Draft report SQL](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/ccpc_erp/report/ccpc_equipment_maintenance_baseline/ccpc_equipment_maintenance_baseline.py) currently joins original Material Issue via Stock Entry→Withdrawal Slip then reads **current** `Withdrawal Slip.equipment`. This is a useful **provisional report only**, not an immutable original-issue Equipment attribution. It now displays an explicit PROVISIONAL provenance warning.
- Existing [real disposable SQL gate](https://github.com/ccpcerp/ccpcerp/blob/review/equipment-maintenance-baseline-2026-10-18/ccpcerp/ccpc_erp/report/ccpc_equipment_maintenance_baseline/test_equipment_maintenance_real_integration.py) previously passed four true ERPNext/MariaDB tests (run `39090992286`), but **those tests did not establish an immutable Equipment snapshot**. New test-first branch changes add a normal update lock test plus multiple issue-item/multiple-Equipment aggregate verification. Record their exact outcome before any upgrade of testing claims.

## Proposed canonical issue-time source — separate schema and accounting review required

1. For each **submitted original** Withdrawal Slip Material Issue row, retain a **write-once, company-validated original Equipment Registry identity** and its linked original Withdrawal Slip **and Withdrawal Slip Item** in the source Stock Entry Detail. Proposed distinct custom Link field `ccpc_equipment_at_issue` or an explicitly authorized existing independent Equipment snapshot field. Do not repurpose a potentially editable current field without proving immutability and migration compatibility. The exact field name and schema are **not approved**.
2. Populate this identity atomically **before Stock Entry submission** from the authorized, validated `Withdrawal Slip.equipment`, preserving the approved original Company and original beneficiary Department. Do not derive it from Equipment's current owning Department at report time or from currently assigned Asset. Enforce consistent item/header Equipment and nonblank provenance for equipment-attributed issues; missing/ambiguous source must fail according to approved exception treatment.
3. Block user/API edits to the stored original identity on draft/submit and subsequent document modifications and enforce original row-link immutability. Submitted vouchers should follow normal ERPNext immutable/cancellation semantics. Administrators' raw SQL still bypasses application validators; restrict database writes, preserve audit logs/backups, and use reconciliation checks to expose inconsistencies. Avoid claiming absolute tamper-proof protection.
4. For each traceable **Stock Ledger Entry** from the submitted Material Issue, join by **exact** `voucher_no` and `voucher_detail_no` to its original item. The maintenance report groups by **issue-time snapshot**, not mutable current Slip/Job Order/Equipment master Department. Cross-check original Slip and current fields as evidence, flag mismatches for a separate audit report, but **do not silently reallocate historical costs**.
5. For multiple items, partial issues, amendments, cancel/reissue flows, Equipment-to-Asset reassignments and multi-Company cases, preserve source identity per item. Never silently select a fallback Equipment or merge costs from another Company.
6. For historic submitted issue items lacking a confirmed original source identity, choose a **separately approved audit/reconciliation procedure**; report them as **unattributed/needs review**, not as zero costs, and never automatically overwrite financial or inventory history/backfill from today's mutable Equipment value.
7. Authorized physical material returns under Option A must reference original submitted issue row and inherit the **original Equipment identity** and original posted valuation/account/Cost Center/Department. Subtract only independently approved, actually posted accepted returns; protect cumulative quantities, duplicate/concurrent receipts and cancellation reversals; avoid double-counting material and Purchase Invoice transactions.
8. Job Order historical Equipment is also a separate provenance concern; current real report reads `Job Order.equipment` and `date_assigned`. For trustable equipment service history, independently review post-close edit controls, Work Request and Equipment Asset Assignment links. No labor rate, outside vendor cost or downtime estimation is authorized by this snapshot design.

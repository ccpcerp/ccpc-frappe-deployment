## 2. Verified source observations — release provenance

- The release config pins `FRAPPE_REF=v16.33.1`, `FRAPPE_SHA=988e54f3c4c291e2077a83809663f123731abe76`; `ERPNEXT_REF=v16.34.2`, `ERPNEXT_SHA=4048fb70e14d1843956fcdabb7c3cca75a1cbcdd`; `CCPC_SHA=cfcc19394a6646548f2b7050db040c8cf5ebafde`. It also pins a specific CCPC ERPNext patch SHA-256 and post-overlay state SHA-256. Containerfile builder compares checked-out commits and patch state during image creation, then **removes app .git directories**. These are useful *build-input checks*, not an independently reviewed immutable **output image** identity.
- `images/custom/Containerfile` has **no** `LABEL org.ccpc.frappe.sha`. Step 125's `_verify_image()` demands precisely that label from the backend image. The current draft verifier therefore has a likely fail-closed incompatibility with its actual image build; do **not** invent a label, self-approve a digest, or bypass verification to make tests green. Image provenance labels should be reviewed as separate build changes and cannot alone certify image contents.
- Dockerfile starts from a **version-tagged**, not content-digest-pinned `python:3.14.2-slim-bookworm` base, and downloads other build-time packages/tools. `overrides/compose.mariadb.yaml` uses `mariadb:11.8` by **tag**, not an immutable digest. `compose.yaml` has `pull_policy: ${PULL_POLICY:-always}`. Do not treat mutable tags or `CUSTOM_TAG` as approved immutable identities. Image IDs and release provenance must be independently reviewed and immutably recorded *after an authorized build*, before Docker runtime attestation.
- Step 125 `ApprovedRuntime` demands immutable backend/DB image IDs and backend/DB Docker Compose **config-hash labels**, exact project and named volumes. No externally reviewed approved release manifest or actual running image IDs, Compose config hashes, project name or Docker volume identity has been established yet. **Never fill manifest expected hashes by reading the same untrusted instance being evaluated.**
- `images/custom/Containerfile` declares `VOLUME ["/home/frappe/frappe-bench/sites", "/home/frappe/frappe-bench/logs"]`, but `compose.yaml` explicitly maps `backend` only to the named `sites` volume. Docker normally provisions an **anonymous volume** for an image-declared `VOLUME` without an override. Step 125 `_verify_mount()` currently requires `len(Mounts)==1` for `backend`, so a genuine backend container may fail the checker due to its `logs` mount. This is a **source-derived compatibility risk**, not a runtime observation. Do not weaken protection to allow arbitrary extra mounts; design an exact approved mount inventory for `sites` **and** a separately accounted log volume if it actually appears, then validate with isolated inspection and offline regressions.
- `scripts/modules/docker.sh` can verify an image exists and records image ID/size, but that is not a signed provenance attestation. Its existing build process uses changing external package sources. The base image and MariaDB image digest, built image ID, Compose spec and release approvals must be handled separately.

## 3. Proposed trusted release manifest — schema concept, NOT populated

A future **operator-reviewed, versioned, non-secret, immutable release record**, independently approved via GitHub review/controlled release process, should contain:

| Category | Required non-secret fields and evidence |
| --- | --- |
| Release/authorization | Unique release ID, UTC preparation/approval time, approved reviewer, release status, parent PR/branch relationships, deployment checkout full Git SHA; no values copied blindly from live Docker |
| Source/build inputs | FRAPPE/ERPNEXT/CCPC commits, approved patch file SHA-256 and overlay state SHA-256, Dockerfile/build-context SHA, dependency lockfiles/constraints if available, reproducibility caveats |
| Container images | Backend and MariaDB immutable **image IDs** (`sha256:...`) from independently verified build/pull, base image and DB manifest digests where available, registry digest or provenance artifact, signed/checksummed build record, expected explicit image metadata label if separately implemented |
| Compose deployment | Exact approved Compose file ordering and contents, profile `dedicated-pre-tls`, project name, reviewed expected backend/db Docker Compose config-hash labels derived at controlled preparation; don't publish plaintext `docker compose config` containing interpolated DB credentials |
| Runtime identity | Host `ccpcerp-prod`, site `ccpcerp.local`, services `backend` and `db`, full approved image IDs, volume names and **explicit allowed per-container mount destinations/types**, expected stable state/health |
| Controls and recovery | Manifest format/version, reproducibility assumptions, backup policy version, intended storage/NAS identity, separate references to *secret recovery procedures*, release verification/rollback approvals, trusted digest of manifest itself |

**Trust rules:** verify release manifest source/signature/protected review status independently of Docker and the application checkout; reject blank, placeholder, changed or unapproved fields. Treat generated runtime labels as *observations to compare to approved expectations*, never as proof of their own integrity. Never include passwords, site configs, database connection strings, private SSH keys or encryption key material in GitHub. Until a real image build/release is independently approved, there are **no valid observed image or config-hash values to record**. Maintain a draft schema, not fake credentials or digests. Release manifest should remain separate from a job-produced backup manifest.

## 4. Verified source observations — backup consistency and side effects

**From pinned upstream Frappe source**:

1. `bench --site ccpcerp.local backup --with-files --ignore-backup-conf --backup-path <isolated path>` passes site backup options to `scheduled_backup(... force=True)` and into the backup generator. It creates a SQL gzip, copies `site_config.json`, then archives public files and private files in **separate sequential steps**. Four files and matching timestamps do **NOT** mean the DB and filesystem correspond to one moment.
2. For MariaDB, Frappe's dump helper includes `--single-transaction --quick --lock-tables=false`. This can give transactional table contents a consistent snapshot **within the database**, subject to InnoDB, DDL/concurrency and engine limitations. It **does not freeze ERPNext transactions, external integrations, file uploads or the public/private archives**, nor guarantee transaction-consistent backups of nontransactional tables.
3. `backup_files()` shells out to TAR and catches a `file changed as we read it` error, **printing a notice and continuing** rather than always failing. Therefore exit status zero and a structurally valid TAR do not certify source files were stable through capture.
4. `new_backup()` unconditionally invokes `delete_temp_backups()`, which scans Frappe's default `get_backup_path()` and removes files older than a configurable threshold (default code `23` hours). **This side effect can occur even when `--backup-path` points at a fresh separate directory.** It must be examined against valuable existing backup contents and prevented by an approved isolated test/data-safe design before ever running live. Do **not** run Frappe's backup as-is against OLD PROD or shared DEVELOPMENT under this approval.
5. Frappe `backup` supports partial DocType include/exclude configuration and optional backup encryption. Step 124 currently requires `--ignore-backup-conf` and assumes `encrypt_backup` is disabled. These exact runtime settings have **not** been checked; encrypted outputs require an independent key escrow and restore procedure, not a silent downgrade.
6. Frappe `delete_if_step_fails` deletes the *newly targeted output path* if an individual backup step fails, and the backup command may roll back generated artifacts on exception. This is another reason to dedicate a new isolated run directory, record failure state and avoid reusing existing paths. No Frappe v16 actual-run test exists on a disposable site.

## 5. Proposed DB/files consistency contract — no runtime action authorized

**Recommended default for an initial independently approved integration test: an isolated maintenance/quiescence window rather than claiming online atomicity.**

- **Before freeze:** approve a documented maintenance window and responsible owner; establish a verified, isolated disposable Frappe test site and database with separately controlled data. Review every writer: HTTP/web/mobile sessions, API integrations, scheduled jobs, background queues/workers, websocket/event handlers, automated imports, file uploads, print/export/media generators, accounting/inventory operations, webhooks and custom CCPC intercompany or billing jobs. A frontend-only maintenance message or `bench pause` does **not** demonstrate all writers have stopped.
- **Quiescence proof (future design):** prevent new writes at ingress *and* integration endpoints, pause/stop schedulers/workers under explicit maintenance approval, drain or account for in-flight transactions, record a validation barrier with DB connection/transaction state and site file state, verify no active writers throughout capture. Define observable proof, fail/timeout conditions, rollback/restart protocol, and emergency abort. Exact mechanisms remain UNDESIGNED for this deployment and must be tested without touching live PROD.
- **During capture:** with the same maintained freeze, execute the version-verified Frappe `--with-files` four-artifact backup and record start/end UTC timestamps, DB snapshot/backup exit, file/archive validation, business document-to-attachment reference checks and immutable artifact SHA-256s. **Never release quiescence before the last file archive completes**, if adopting a full freeze. Check TAR warning/changed-files diagnostics, generated file inventory and any Frappe cleanup effects. A copied DB alone is not complete.
- **After capture:** independently verify the source/capture set, restore normal services only via approved procedure, record freeze duration/failed operations and actual feasible RPO/RTO. Then copy/publish to verified new NAS share using a separately approved mount lifecycle and Step 123's fail-closed rules. **No automatic retry after uncertain success**.
- **Alternate future options:** investigate coordinated database-and-site-volume snapshots or continuous online methods only if independently verified to provide a valid common consistency boundary and tested with real Frappe/MariaDB data. An InnoDB single-transaction dump plus a separately timed file TAR cannot be declared atomically synchronized. Do not choose host-wide snapshot or filesystem freezing on any shared infrastructure without new approval.

**Priority validation cases in isolated DEVELOPMENT/disposable environment (NOT run now):** upload during dump/TAR; financial ledger and stock update during backup; custom CCPC cross-company posting; queue job completing midcapture; tar changed-file warning; nontransactional table/DDL; a multi-file upload midway; failed dump, archive, clean-up and network transfer; restore mismatched DB/file pair and verify detection; Frappe default-backup-dir retention side effects; capture encryption on/off; abnormal disconnection and quiescence recovery. Restore drill must include database/inventory/ledger and public/private attachments, not only checksum passes.

# CCPC Withdrawal Slip — Stockroom Peer-Issuance Policy and Server-Side Design

**Owner business decision:** 2026-10-14. **Status:** approved policy; **planning/review only**, *not* approval for implementation, application-code changes, site schema changes, user creation, stock/GL posting, deployment, or PRODUCTION.  
**Policy selected:** **Option A** — a Stockroom employee may request supplies for their own consumption, including office supplies; another Stockroom employee must physically issue and post the same Withdrawal Slip. **Routine manager approval is not required.** There are approximately five Stockroom employees and the manager is often unavailable.  
**Code source reviewed:** `ccpcerp/ccpcerp`, draft PR [#7](https://github.com/ccpcerp/ccpcerp/pull/7), branch `feature/withdrawal-material-issue-safety`, exact verified head `85d129e193b32cc229de2e30145359bb3979c257`; base `review/intercompany-approval-failure-tests` at `806fa23516490ec7beefcff03a1baa09d722120e`. App changes proposed below are **not implemented**.

## 1. Business operation — agreed examples

| Scenario | Request/preparation | Approval per existing workflow | Stockroom issue and recording | Allowed under Option A? |
| --- | --- | --- | --- | --- |
| Maintenance colleague requests office supplies | Maintenance Requestor | Existing Requestor transition `Approve & Send to Stockroom` | An authorized Stockroom employee | Yes; normal issue |
| Stockroom employee Juan needs two ballpens | Juan creates own slip | Existing Requestor transition; no routine manager | Another Stockroom employee, Pedro, checks, releases and posts | Yes |
| Stockroom employee Juan needs two ballpens | Juan creates own slip | Existing Requestor transition | Juan attempts to issue and post that slip | **No**; reject in server-side validation |
| Juan requests for himself, Pedro begins review, Maria issues | Juan | Existing workflow | Maria releases/posts | Yes, provided issuer really is different from Juan |
| Exception: only one Stockroom employee available | That employee may prepare slip | Existing workflow | **Leave unissued** until a different authorized employee can verify/post; a documented exception process requires a separate future policy | No routine bypass |

The peer issuer must act under **their own ERPNext user account**, inspect the request and quantity, record receipt accurately, and submit the linked Material Issue. Shared logins or pretending to be another user defeat the audit control. This policy does not prevent a Stockroom employee from being a requester.

**Important distinction:** Existing `Approve & Send to Stockroom` is a **Requestor-owned self-approval transition**, not an independent supervisor authorization. Option A deliberately leaves this routine transition in place and adds a different-person physical issue/posting control. Whether to rename the transition to avoid misleading 'approval' language is a separately reviewed usability choice.

## 2. Verified current implementation and gap

- In the installed isolated test-site Workflow, all eight states are draft `doc_status=0`. `Draft→Approved` is allowed Withdrawal Slip Requestor with `allow_self_approval=1` and no condition; `Approved→Stockroom Review` is allowed Stockroom Personnel, same self-approval allowance. Stockroom may return a slip for correction; Requestor can reapprove conditionally. `tabDocPerm`: Stockroom Personnel read/write on Withdrawal Slip, Requestor read/write/create with `if_owner=1`. No matching Stock Entry DocPerm for these two roles.
- Both branches' `User.before_save` hook (unchanged `setup.py`/hooks source) automatically grants `Withdrawal Slip Requestor` to Stockroom System Users when the role exists. On the isolated site `MRS Requestor` and `CCPC Stock Inquiry User` role records were not present. Thus a Stockroom employee is expected to hold **both** Requestor and Stockroom permissions; this is not itself a violation if same-slip separation works.
- Withdrawal Slip DocType field `requestor` is **Autocomplete (free text)**, *not a User link*; `received_by` is Data free text; `approving_supervisor` is a read-only **User Link labeled "Prepared By"** set from the authenticated creator on first validation. The standard `owner` identifies the document creator. `issued_by` is read-only Link User populated from `withdrawal_slip_issued_by` on submission. Therefore comparing display names or `received_by` to a user account is unreliable, and `approving_supervisor` should **not** be called an independent approver identity.
- `withdrawal_slip_stock.py` provides two whitelisted POST endpoints: `make_material_issue` (legacy draft for users with ordinary Stock Entry create permission) and `issue_withdrawal_slip` (scoped insert/submit without broad Stock Entry roles). The `Stock Entry` hooks include `validate`, `before_submit`, `on_submit`, `on_cancel`. The existing parent row-lock (`SELECT ... FOR UPDATE`) covers current status, received_by, company and warehouse, not slip creator/requester identity. **No same-slip Requestor-vs-Issuer identity check exists at issue time.**
- Test coverage prior to this policy: 12 new and 35 regression **mocked** tests passed; no live Frappe user/role/issue/GL/SLE/rollback or MariaDB concurrency integration tests. Site-free exact feature module and hook imports passed. Isolated site has 11 protected recovery checkpoint sets (44 archives; no restore drill); no test user or Material Issue yet created.

## 3. Proposed enforceable server-side design — NOT IMPLEMENTED

**Decision to implement with a separate authorization later:** an authenticated Stockroom user may issue a Slip only when that user is **not the employee requesting the materials for themselves**. Since the current `requestor` is free text, preserve the desired semantics only with reliable server-side identity, not unverified string comparison.

1. **Immutable request identity**: Design an explicit, canonical `requestor_user` or `withdrawal_requested_by_user` **Link → User** for Stockroom self-service withdrawals. Stamp or validate it using the authenticated requester, keep immutable after first save, and set/verify it independently of UI-supplied display names. Confirm how to handle requests created by clerks *on behalf of* other people and employees without logins. This is a proposed schema/design question, **not a field to create under current authorization**.
2. **Conservative protection before identity is available**: For a new self-originated Slip, the built-in `owner` and `approving_supervisor` (creator/Prepared By) can supply trustworthy identity anchors. A shared helper should reject a current issuer equal to the original creator/preparer, using an immutable server-side identity or audit-backed originator. This is intentionally stricter than the narrow self-consumption requirement for slips prepared by Stockroom *on behalf of other colleagues*, so **review that legitimate scenario before implementation**. Do **not** rely on editable Autocomplete `requestor`, editable Data `received_by`, client JS or merely comparing names. Do not let editing `owner`, copying a slip, or choosing a different `received_by` bypass the rule.
3. **Single locked source of truth**: Expand/adjust the existing parent row-lock query to return the immutable requester/creator identifiers and compare with the loaded document after lock acquisition (avoid stale REPEATABLE READ snapshots). If identity cannot be established reliably, **fail closed** before financial posting; no permissive fallback. Keep the row lock and all operations within the request transaction, without manual commit.
4. **All entry points**: Run a shared peer-issue assertion after the role + Slip write check and **before any privileged insert** in `issue_withdrawal_slip` and legacy `make_material_issue`; invoke it **again in the Stock Entry `before_submit` hook** for manually constructed/altered linked Stock Entries. `validate` may provide early feedback but cannot replace `before_submit` as a final backstop. For Administrator/System Manager bypass or recovery, require a separately reviewed audited emergency policy; do **not** silently exempt powerful roles.
5. **Audit trace**: Preserve `issued_by` as the actual authenticated issuer recorded on linked Stock Entry submission, retain the real received-by party and identify the requester with a durable canonical User ID wherever possible. No overwriting existing posting identity or transforming a manually edited name into "verified" identity. Protect identity fields from unauthorized changes at Frappe controller/server level, not UI read-only flags alone.
6. **Workflow UX**: Requestor may still use `Approve & Send to Stockroom` without manager; a colleague may use `Start Review`, adjust quantity/shortage notes and `Issue Materials`. Optionally hide Issue Materials for creator as convenience, but **server rejection is mandatory**. Determine whether the requester should be prohibited from `Start Review` as well; Option A explicitly requires a **different issuer**, and blocking self-review is optional defense-in-depth needing a separate review.

## 4. Risk and negative-path review before any implementation

- **Ambiguous requester identity:** Current free-text `requestor` means a slip created by employee A for employee B can be mistaken as A's own. Decide handling for clerks creating on behalf before committing to an overly broad all-slips `owner != issuer` gate.
- **Workflow bypass and direct submit:** Issue endpoints and Stock Entry `before_submit` must both reject same-person issuance; verify no alternate linked or unlinked Stock Entry bypass. **Unlinked general-purpose Stock Entries** are governed by standard ERPNext stock permissions; this policy cannot by itself prevent misuse of those rights, so avoid granting broad Stock User/Manager to routine Stockroom staff and audit who possesses it.
- **Identity tampering:** UI read-only state, custom requestor text and Received By text cannot authenticate identity; check `owner`, `approving_supervisor`, any new Link/User IDs, and change history server-side. A malicious direct API request must not substitute a colleague's identity.
- **Concurrency/accounting:** Keep existing row-level lock + submitted issue recheck, regular ERPNext stock/GL validations and single transaction; reject failed assertions before any `ignore_permissions`-assisted insertion, and use `before_submit` as backstop. Mock tests do not replace live MariaDB row lock and end-to-end rollback checks.
- **Legacy slips and migrations:** New User-link field may require an explicitly approved schema change; existing slips lack a trusted requester ID. Define fail-closed legacy policy and a separately audited mapping/retention plan. Do not backfill from free text without verification; no migrations or schema modifications under current authorization.
- **Audit of personal access:** Two Stockroom identities must be independently authenticated and must not share passwords. Test role auto-assignments and verify no unintended Stock Entry create/submit via combined roles. No new production access or role changes planned.

## 5. Future acceptance criteria (not tested yet)

1. Stockroom A creates their own Slip, uses existing Requestor transition; Stockroom A **cannot issue** it through Issue Materials, legacy draft-then-submit, direct linked Stock Entry, or forged field values. No Stock Entry, SLE, GL, Bin or Slip status changes on denial.
2. Stockroom A creates their own Slip; Stockroom B starts/reviews it, accurately verifies item/quantity, issues and posts through the scoped POST endpoint. Submission creates exactly one linked Stock Entry, authenticates **B** as issuer, records **A** as requester/receiver where appropriate, and reflects expected Bin/SLE/GL posting.
3. Nonstockroom Requestor C's Slip follows current workflow; Stockroom A may issue it if independently authorized and distinct from the actual requester. Creation *on behalf of C by A* needs an explicit design test because owner-only enforcement may reject it.
4. Same-person issuer attempt with tampered `requestor` and `received_by` values fails; document owner/preparer and canonical identity cannot be altered postcreation to evade the control.
5. Role-permission matrix, positive and negative cases under true non-Administrator sessions; direct API POST protection; repeat issue, double POST concurrency, stale-read, and failure/rollback tests pass on isolated MariaDB with stock/GL independently audited.
6. No regressions in 47 existing mock-only suites, draft/review workflow, stockroom shortage reason rules, issue quantity integrity, or unaffected general Stock Entry types. Do not call source tests site integration tests.

## Blocking findings — must resolve before any one-unit posting authorization

**B1 — Critical: writable database endpoint is not intrinsically constrained to isolated DEVELOPMENT.** Candidate lines **350–360**, **389–395**, **303–309**, **327–345** compare only configured database names and readback `SELECT DATABASE()`; the independent readback allows `iso.get('db_host') or common_settings.get('db_host') or '127.0.0.1'`. It does not enforce DEV `mariadb:3306` or independently compare active SQL connection/server identity against the verified DEVELOPMENT database service. Earlier *read-only* boundary and DB preflight passed, but an execution-time mutating script must independently fail closed on exact site, server endpoint and PROD separation without reading/writing PRODUCTION business data. Remedy: incorporate reviewed DEV-only host, port, named Compose service/container and selected DB identity checks **before** connecting with a write-capable session; use an independent preflight or bound server identity with no fallback to unknown hosts. Review permissions, mounts and environment differences.

**B2 — High: document-level insert/submit guards do not enforce a database-wide write allowlist.** Candidate lines **430–544** wrap `Document.insert`/`submit`, but Frappe itself uses `Document.db_update`, `frappe.db.set_value` and direct SQL; `Document.insert` may create child records via lower-level paths. Pinned ERPNext `Stock Entry.on_submit` invokes stock-ledger updates, GL creation, repost and related document/quantity functions (ERPNext stock entry lines **580–610**). The candidate checks main table counts but does not record/assert an exhaustive before/after delta for all other tables or disallow raw SQL transaction-control/DDL paths. Patching `frappe.db.commit` alone does not stop `frappe.db.sql('COMMIT')`, direct connection operations or implicit DDL commits. Remedy: review/trace entire reachable DML & transaction path, authorize only necessary writes and ensure no other committed records/side effects; devise isolated negative tests for denied unexpected writes/implicit commits. Do not blindly monkeypatch unknown internals in a live commit attempt.

**B3 — High: callbacks can perform postcommit Redis operations after SQL is already durable.** Frappe `Document.run_post_save_methods` (`frappe/model/document.py` lines **1445–1475**) calls `notify_update`, which schedules `frappe.publish_realtime(..., after_commit=True)` (lines **1493–1513**). Pinned `frappe/realtime.py` lines **73–90** registers a `frappe.db.after_commit` callback and **100–115** publishes via Redis; pinned `Database.commit()` runs `before_commit`, issues SQL COMMIT, then runs `after_commit` (lines **1176–1194**). Candidate only patches `frappe.sendmail`, `frappe.enqueue`, `background_jobs.enqueue` and instance `frappe.db.commit` during the transaction. It does not inventory or explicitly accept/deny the `after_commit` callbacks or other Redis/outbound events. A callback failure after the SQL COMMIT may be shown as uncertain; callback side effects cannot be SQL-rolled back. Remedy: identify, validate and either safely suppress or narrowly authorize precisely anticipated callback events on the isolated site; test failure-injection before/after the durable commit and audit Redis/external effects. Do not misrepresent suppression as verified until tested.

**B4 — High: expensive SHA256 of 48 backup files occurs while the stock/Slip SQL transaction holds locks.** Candidate lines **550–596** begin the transaction, save `received_by`, acquire a `Withdrawal Slip` `FOR UPDATE` lock through the handler, post stock/GL, then **588–589** rehash all 48 archive files while still uncommitted and holding locks. Additional rehash occurs after the commit. This can extend lock duration and raise deadlock/timeout risk, especially when archives are large or storage is busy. Remedy: shift bulk recovery hashing to a clearly scoped read-only preflight outside the write transaction, then use a bounded low-latency precommit gate (e.g. immutable manifest/version/source metadata with an explicit change-control boundary). Revalidate critical current SQL invariants while locked. An earlier standalone read-only audit has already hashed the files twice but does not establish recoverability.

**B5 — High: the strict ancillary DocType allowlist lacks a commit-capable-path dry-run/fault-test proof.** Lines **471–477** admit only narrowly scoped `Version` inserts plus Stock Entry/SLE/GL, while ERPNext's Stock Entry submit has many conditional branches (stock reservation, project, repost, serial/batch, related docs). Some are expected to be inactive for this synthetic fixture, but a code-only assumption is insufficient; a newly surfaced legitimate auxiliary insert will STOP and consume the one-shot marker or leave caches modified. Remedy: unit-test the guards offline with realistic mock objects, trace all real synthetic-fixture side effects with separately approved **rollback-only** *new* test artifact (not the consumed diagnostic) before any permanent COMMIT; only add explicitly necessary ancillary write permissions with before/after assertions. Never relax to “allow all”.

**B6 — High: recovery strength is insufficient for blanket claims of reversibility.** Before/after SHA256 checks show no mutation *during one run* of the 48 local isolated-site artifacts; they do **not** prove backup archive contents are valid, independently match a trusted off-host manifest, exist on a separate host, or have been restored into an isolated disposable target. If SQL COMMIT partly succeeds or after-commit callbacks fail, blind restore/retry is dangerous. Remedy: review an independent, non-production recovery strategy for isolated test only; demonstrate archive readability and, if practical, a controlled disposable restore drill with separate explicit approval. Do not touch backups or PRODUCTION to resolve this under current scope.

**B7 — Medium: one-shot marker and failure boundary need additional adversarial tests.** Candidate lines **11–27** accept an environment variable as a safeguard, place a marker under the operator-controlled staging directory before Docker preflight, and do not reject a symlink for `$HOME/ccpc-reviewed-scripts` itself. It conservatively treats attempted COMMIT as persistence-unknown and never retries, which is good, but any harmless preflight error consumes the attempt marker, and unexpected `BaseException`/signal/kill paths bypass the sanitized `except Exception` branch. Remedy: require external owner approval plus exact SHA/immutable Git pin (not merely env variable); ensure private directory/path/mount checks, durable attempt status/exit handling and separate safe read-only reconciliation for interrupted/unknown outcomes. Never delete the marker to force replay.

**B8 — Medium: the main-posting and accounting invariants are tightly tailored to one fictional fixture, not a generalized release claim.** The test assumes 1 Nos, 10→9 Nos, approx PHP100 adjustment debit and stock-in-hand credit, total precisely one new SLE and two new GL rows. Those guards are suitable only for the clean synthetic site validated in the current read-only audit. They do not establish CCPC's eventual real-company expense-account policy, v16 HTTP/CSRF behavior, concurrent double-submit safety under separate database sessions, or PRODUCTION viability.
